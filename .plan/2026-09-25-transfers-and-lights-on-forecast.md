Design decision (planner, owner feedback item 2): the spending group is the category's one `type` field, with five values: `income`, `transfer`, `fixed` (Fixed payments), `lights_on` (Keep the lights on) and `occasional` (Occasional payments). `variable` is gone: it is split into `lights_on` and `occasional`. This beats the previous `variable` + separate lights-on set, and a `variable` + boolean flag: one field, one select in the UI, no invalid combination (a ticked `fixed` category), no second table that drifts when a category is renamed, and every consumer keeps reading the same `category_types` name → type mapping (recurrence.py:48, recurring.py:147, monthly.py, dashboard.py), so the column keeps the name `type` and only the UI calls it "Group". Recurring detection keeps its meaning: recurrence.py:23 excludes `lights_on`, `occasional` and `transfer`, exactly what `variable` + `transfer` excluded before; `fixed`, `income` and uncategorized rows are still detected. `spending_groups.py` (N02) holds the five values, their labels, the detection exclusion and the per-group sum; nothing else hard-codes a type string. A legacy TOML with `variable` (the owner's file) imports Groceries, Transport and Shopping as `lights_on` and every other `variable` category as `occasional`; the owner adjusts groups on the Categories page.

Categorization config (owner feedback items 1, 3, 6): categories and ordered rules live in two DB tables (migration 0006, N03) and are edited on `/categories` (linked from Settings and Uncategorized; N08, N09). Every change re-applies the rules and re-runs recurring detection, as import and startup already do. The app never reads a TOML at runtime; `uv run sonar import-categories PATH` replaces the DB taxonomy from a local TOML once (N05). The repo seeds generic categories and no rules. The own-transfers IBAN rule for the joint sub-account is not a repo change: the owner adds it locally at N13, using the joint sub-account's IBAN, looked up locally.

Categorization API (owner answer Q1): Claude Code categorizes through JSON endpoints under `/api/` on the running app (N17), not through files or direct DB access. One service layer, `src/sonar/taxonomy_service.py`, owns everything between raw input and the store: the re-apply helper (N05), input parsing of the category and rule fields (the HTML form and the JSON body use the same field names: `name`, `group`; `category`, `counterparty`, `counterparty_regex`, `purpose`, `purpose_regex`, `sign` any/debit/credit, `iban`, `creditor_id`, `min_amount`, `max_amount` as euro text, `position`), the friendly error text as `TaxonomyError(message, field)`, the read views, and "every write re-applies rules and re-runs detection" (N08, N09). The page routes in app.py and the router in `src/sonar/api.py` only translate HTTP to service calls: the page re-renders with `#form-error`, the API answers 400 `{"error", "field"}` or 404 `{"error"}`. No auth, bound to 127.0.0.1 like the rest of the app; API writes accept only `application/json` bodies (a cross-site HTML form cannot post JSON without a CORS preflight, which the app never grants). The Uncategorized export header stays `Categorization request: follow the Categorization workflow in CLAUDE.md.`, and that workflow (N11) is: use the running app, GET categories, rules and uncategorized groups, propose exact changes, write only after the owner confirms, report in at most 5 lines; no repo file or test changes.

Forecast (owner answer Q2): `variable_forecast.py` is replaced, not redefined. `lights_on.py` works on the same months as the Monthly page (salary months from real salary dates, calendar months without a salary day, monthly.py:110-137): expected = the day-weighted daily average of the last 3 complete months × days; range = lowest and highest monthly daily average × days. Forecast = Fixed payments due + Keep the lights on; Occasional payments and uncategorized debits are not forecast (owner answer Q3) and stay visible on Monthly and the trend page.

Personal data (owner feedback item 5): no tracked file or commit message added by this plan may contain a real name, IBAN, creditor ID, landlord or municipality name. Checks compare against the values in the local `data/categories.toml` (gitignored, created by N11) and never print them into tracked files. Tests use fake strings and the standard example IBAN only.
