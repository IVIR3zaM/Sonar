# N16 owner Gateway replacement and coexistence
Do: The owner pushes Gateway and lets its workflow apply, forcing a blue/green VM replacement. Gateway's workflow must then redeploy Sonar and Kita automatically, and all three must serve. Finally, a local terraform run in each repo must still work on the R2 backend.
Context: Push with `git -C ../Gateway push origin main`; the workflow validates, then applies in `production`.
  If that apply did not replace the server (the N02 stats.sh change was already applied), run Actions → Gateway's workflow → Run workflow with `replace_server` = true (D27).
  Watch: the new VM passes its readiness gate, the DNS flips, and the old VM is destroyed. The job sees the new server id and dispatches Sonar's and Kita's `ci.yml` (D17).
  An app run that started while two servers matched the label fails its exactly-one-server postcondition; re-run it (D18). Sonar's volume reattaches to the new VM and its DB is intact.
  On the VM, `nginx -t` passes with Gateway's config plus `conf.d/sonar.conf` and `kita.conf`.
  Locally, in all three roots: `terraform plan -lock-timeout=10m` shows nothing beyond the SSH source IP; then run one `terraform apply -lock-timeout=10m` in each.
Done when:
- C1 [cmd] `gh run list -R IVIR3zaM/Gateway --branch main --limit 1 --json conclusion --jq '.[0].conclusion' | grep -qx success`
- C2 [cmd] `for r in Sonar Kita; do gh run list -R IVIR3zaM/$r --workflow ci.yml --event workflow_dispatch --limit 1 --json conclusion --jq '.[0].conclusion' | grep -qx success || exit 1; done`
- C3 [human] The VM was replaced, and afterwards Gateway's site, Sonar (sign-in and existing data) and Kita all serve; `nginx -t` passes on the new VM.
- C4 [human] The local apply in Gateway, Sonar and Kita each succeeded on R2; Gateway's plan shows no `firewall_ids` drift; Gateway's run log shows no domain, path, link or token.
